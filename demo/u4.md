# U4 — a stock phone browser plays a lent film and seeks

Gate, U4's bar as PLAN §4 words it: **a stock phone browser plays a lent
film and seeks.** It is run on Safari on an iPhone and on Chrome on an Android
phone. Each seek's time is recorded beside Demo A's bar of 5 s, the measure
u4-6 used. Each phone leaves a record. A phone that stops on the way is a
recorded failure, never a skipped one.

**Before the run.** This needs an https origin to serve the page from: service
workers and WebCrypto run only on https (or localhost), so a phone cannot use
the page from `http://<the computer's address>`. Sam's computer runs `svrngs`
and lends the film. The dry run of 2026-10-05 (`runs/u4/2026-10-05/`, its
README) took these steps on one computer, in Playwright's Chromium and WebKit.
Its three findings were fixed by u4-9 before this run, and the dry run was
run again (`runs/u4/2026-10-05-reach/`): WebKit now reaches n0's relays
(`ralph/REVIEW_FINDINGS.md` #52); no seek waits for a range that runs on to
the film's end (#53); a cold join fetches the wasm once (#51). There,
Playwright's WebKit as an iPhone joined through n0 in 5.6 s from opening the
link, and played on after each of 15 seeks within 3.4 s.

**Run again after u4-10: Safari on the iPhone.** On 2026-10-05 Firefox on the
operator's iPhone joined and played through n0
(`runs/u4/2026-10-05-phones/iphone-firefox.json`). Safari 26.6.1 on iOS 18.7,
on the same phone and the same origin, joined but did not play: "The computer
lending this did not answer." The worker's trace at `<origin>trace` showed
why. Safari's service worker read no sealing key where its page had kept one,
made one of its own over the page's, and failed to unseal, so it never
dialled. u4-10 fixed it in three parts. Only the page makes the sealing key.
The page hands its worker the person's key in memory when it opens the group.
A worker that holds no key, for example one the browser stopped, answers a
lend's address with a short "Opening…" page, which hands the key over and
opens the address again. In Playwright's Chromium and WebKit, a worker planted
to read no seal plays the film by the handed key, and again after it is
stopped (`a_worker_that_reads_no_seal_dials_with_the_key_the_page_hands_it`,
crates/svrngs-node/tests/browser). Playwright's WebKit never had Safari's
fault, so only the iPhone can say whether it is gone. Safari on the iPhone is
the run to repeat first.

## 1. Build the page and publish it to an https origin

On this Mac, from the repository root. Install binaryen first if you want the
smaller wasm, which `scripts/build-web.sh` then runs `wasm-opt -Oz` on (the dry
run had none):

```sh
brew install binaryen
scripts/build-web.sh --out target/web/site
```

Any static https host works if it does three things: serves the directory at
a path ending in `/` (the root is simplest); serves `.wasm` as
`application/wasm`; and does not mark `index.html` or `sw.js` immutable, since
their URLs are the same on every build. Every other file the page fetches,
the wasm included, carries the build's version in its URL (`?v=`), so a host
may cache those for good. With Vercel, whose CLI is on this host (logged in
as `alexbryan-empath`) and whose defaults give all three:

```sh
(cd target/web/site && vercel deploy --prod --yes)
```

Use the production address it prints after `Aliased:`, `https://<project>.vercel.app`.
Do not use the per-deployment URL, which Vercel's deployment protection may put
behind a sign-in. Check it from the Mac:

```sh
ORIGIN=https://<project>.vercel.app/
curl -sI "${ORIGIN}wasm/svrngs_web_bg.wasm" | grep -i '^content-type'   # application/wasm
curl -s "$ORIGIN" | grep -c 'app.js?v='                                  # 1
```

## 2. Sam's group, its link on that origin, and a lent film

Use a data dir of its own, so this computer's own groups are untouched. In one
terminal, left running:

```sh
cargo build --release -p svrngs
export SVRNGS_DIR=~/.svrngs-u4
RUST_LOG=info target/release/svrngs new House --as Sam --origin "$ORIGIN" 2>~/svrngs-u4.log
```

It prints two links. The one to send is `https://<project>.vercel.app/#<token>`,
which works for a day.

In a second terminal, the film. Use any H.264 mp4. A real film is better, and
#53 is about long ones. The dry run's own film, if you need one:

```sh
mkdir -p ~/Movies/u4
ffmpeg -f lavfi -i "testsrc2=duration=120:size=1280x720:rate=24" -vf "noise=alls=12:allf=t" \
  -c:v libx264 -preset veryfast -b:v 3M -maxrate 3M -bufsize 6M -g 48 -pix_fmt yuv420p \
  -movflags +faststart ~/Movies/u4/title.mp4
node demo/runs/u4/2026-10-05/lend.mjs ~/Movies/u4 8700        # leave running
```

In a third terminal (press Enter at the password question):

```sh
SVRNGS_DIR=~/.svrngs-u4 target/release/svrngs share 8700 --kind film
```

Rehearse from the Mac in Chromium before picking up a phone. This joins a
person called Mac to the group:

```sh
node demo/runs/u4/2026-10-05/drive.mjs run \
  '{"engine":"chromium","link":"<the https link>","name":"Mac","lend":"film","seeks":[60,20,100]}'
```

A line with `open_to_name_ms`, `name_to_list_ms`, `first` and three `seeks`, each
with a `plays_ms`, means the origin, the link and the lend all work. A
`stopped` field means something failed, and it says where.

## 3. On each phone

**A phone whose Safari opened the origin before u4-10 clears that site's
website data first.** Safari's old worker had put its own sealing key over the
page's, so the key the page kept then no longer opens. On the iPhone: Settings
→ Apps → Safari → Advanced → Website Data, search for the origin's host
(svrnme.sh, or your Vercel host), swipe it and tap Delete. Then open the link
afresh, which joins again under a name of its own. This is a fresh join
because the old key cannot be recovered.

Turn Wi-Fi off and use cellular, the real case (the page reaches Sam's computer
only through the relay either way). Use the stock browser, Safari on the
iPhone and Chrome on Android, in a normal tab. Record the screen.

1. Open the https link from Messages or email.
2. When the page asks "What's your name?", type one and tap **Join**. Time it
   from tapping the link to "You're in House, as <name>" with **Sam's film**
   listed.
3. Tap **Sam's film**, then play. Time from the tap to the first moving frame.
4. Seek by dragging the scrubber about halfway, then about a quarter, then
   near the end, all within the first ten seconds of play (#53). For each,
   time how long until it plays again.
5. Close the tab, open the link again, and confirm you are in without being
   asked a name. Then lock the phone for a minute, come back, and play and
   seek once more. The browser may have stopped the worker by then (DESIGN §3,
   call 3).
6. Note any word on the page that DESIGN §1 keeps from people: key, member,
   node, relay.
7. If anything stopped, open `<origin>trace` in the same browser, for example
   `https://www.svrnme.sh/g/trace`, and save its text beside the record. It
   holds the worker's last 300 lines, or the lines kept from its last failure.
   A run that got through the "Opening…" page shows the line
   `answered with the hand-over page` there.

## 4. What to record for U4's bar

One record per phone, in `demo/runs/u4/<date>-<phone>.json`, with the
recording beside it and the Mac's `~/svrngs-u4.log`:

```json
{
  "bar": "u4: a stock phone browser plays a lent film and seeks",
  "date": "YYYY-MM-DD",
  "phone": "iPhone 15, iOS 26.x, Safari | Pixel …, Android …, Chrome …",
  "network": "cellular",
  "origin": "https://<project>.vercel.app/",
  "commit": "the svrngs commit the page and the command were built at",
  "joined": true,
  "asked_name_once": true,
  "link_to_list_s": 0.0,
  "lend_to_first_frame_s": 0.0,
  "seeks": [{"to": "half", "plays_again_s": 0.0}, {"to": "quarter", "plays_again_s": 0.0}, {"to": "end", "plays_again_s": 0.0}],
  "reopened_without_asking": true,
  "after_lock": "played and sought | what happened",
  "words_kept_from_people_seen": [],
  "recording": "path to the screen recording",
  "notes": "where it stopped, and what the page said, if it did"
}
```

U4's bar is met when a stock phone browser plays the film and plays again
after its seeks. `joined`, `asked_name_once` and `reopened_without_asking` are
the joining that DESIGN §3 describes, recorded beside it. An iPhone stopping at
"did not answer" is a recorded failure. Playwright's WebKit got past it after
u4-9 (#52), and Safari's own cause was fixed by u4-10, so record what the page
said, save `<origin>trace`, and keep `~/svrngs-u4.log`. A seek
that takes more than 5 s goes in `notes` with how far it jumped (#53).
