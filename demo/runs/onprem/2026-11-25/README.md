# On-prem install, the core loop — 2026-11-25

A prototype of the tool that installs a vendor's service on a customer's
own server, nearly automatically, with no shell for anyone. It knows
nothing about what it installs. The first service it is for turns session
notes into insurance forms for a medical team, but here that service is a
stand-in answering `/health`, by design. Rehearsed on a fresh, air-gapped
Fedora 45 server: a systemd container with no network
(`Containerfile`, `rehearse.sh`). Transcript: `out/transcript.txt`, which is
regenerated by each run and git-ignored.

## The loop

1. **The vendor signs a bundle** (`vendor.mjs bundle`): a recipe, its
   ed25519 signature, and the artifacts it names, by sha256. It goes in on
   a USB stick.
2. **The admin pins the vendor's key once** (`site.mjs trust`), checked by
   fingerprint against what the vendor said outside the bundle.
3. **`plan` changes nothing.** It checks the signature and every artifact,
   then runs the recipe's needs on read-only probes from a closed set
   (`systemd`, `memory`, `disk_free`, `port_free`, `disk_encrypted`). It
   says, in plain words, what the machine has and what it would do, and
   prints a token for exactly that. `--auto` takes the first of the vendor's
   allowed choices that passes (a taken port today).
4. **`apply --token`** re-plans, and runs nothing if the token differs.
   Steps come from a closed set (`user`, `dir`, `unpack`, `unit`, `health`),
   each with its own check. A step already done is skipped, and a unit is
   restarted whenever anything it runs changed. The service runs as an
   account that can't sign in, under `ProtectSystem=strict`, able to write
   only its data folder.
5. **Every step ends in a verdict**: passed, failed, could-not-judge or
   never-ran. Only passed comes without a why, and the journal keeps each
   one. Probes and failures report facts about the machine (sizes, ports,
   unit states, exit codes), never file contents or service logs, so a
   support view of them can't carry patient data.

## What the rehearsal showed (`rehearse.sh`)

| # | Scenario | Result |
|---|---|---|
| 1 | Plan before any vendor is trusted | refused, nothing read |
| 2 | Plan | 4 steps; disk encryption could-not-judge on the container's overlay, as a warning |
| 3 | Port 8610 taken (planted) | STOP, names the holder; `--auto` takes 8611 |
| 4 | Approved, then 8611 taken before apply | nothing ran; the new plan takes 8612 |
| 5 | Tampered artifact | refused at plan, nothing done |
| 6 | Install as approved | 5 passed in about 1 s; `/health` answers 0.1.0 |
| 7 | Plan again | nothing to change |
| 8 | Machine restarts | the service is back by itself |
| 9 | Upgrade to 0.1.1 | only unpack, restart and health ran; answers 0.1.1 |
| 10 | A release that crashes at start | failed, with the unit's state and exit status, no log line |
| 11 | Back to 0.1.1 | passed |
| 12 | The service's reach | `User=notes`, strict, writes only its state folder; loopback only |

The first rehearsal caught three bugs in the tool, fixed before the run
above:
- **The upgrade and the crash both reported "Installed".** The unit wasn't
  restarted, and the health check didn't compare versions, so the old
  process answered in the new one's place.
- **A tampered artifact passed `plan`**, and `apply` ran two steps before
  refusing it.
- **A no-op counted the health check as a step to run.**

## Not yet

- **The vendor's agent on a support link.** Exposing plan and status
  read-only through a lend is the support-link run's channel
  (`../support-link/2026-11-25/`), not built here.
- **Rollback.** After a failed release, the admin applies the previous
  bundle (scene 11). `app.prev` is kept but not restored automatically.
- **Probes and steps the real service will need:** a GPU and its driver,
  model weights as artifacts, TLS, firewall, backups. Each lands as one
  more closed kind with its check.
- **Real hardware.** The disk-encryption probe reads LUKS through `lsblk`,
  but only a container ran here.
- **Node on the target.** The site tool needs Node 22 or later; it should
  become one binary.
- **One rehearsal, one machine image.** These are not rates.

## Run it

    podman build -t onprem-target:f45 -f Containerfile .
    node vendor.mjs key keys
    node vendor.mjs bundle vendor/recipe.json keys bundles/v010
    node vendor.mjs bundle vendor/recipe.json keys bundles/v011 --version 0.1.1
    node vendor.mjs bundle vendor/recipe.json keys bundles/crash --version 0.1.2 --crash
    ./rehearse.sh
